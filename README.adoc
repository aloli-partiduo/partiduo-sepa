= partiduo-sepa — paiements SEPA
:toc: left
:toc-title: Table des matières
:icons: font

*Partiduo* est le portage en Crystal de https://noalyss.eu[NOALYSS], logiciel
libre de comptabilité créé et maintenu par *Dany De Bontridder*. Partiduo
n'est pas un projet officiel NOALYSS.

Ce dépôt est l'extension `SEPA` de Partiduo (ADR-003), successeur de
l'extension « Virements SEPA » de NOALYSS (`noalyss_xmlpayment`, la source
*legacy*) : on en porte les fonctions, pas le code. Les factures
fournisseurs (et, nouveauté, les factures clients sous mandat) sont réunies
en lots, contrôlées, préparées puis approuvées — à une ou deux personnes —,
et le fichier ISO 20022 est produit, contrôlé et conservé en pièce jointe.
Une fois le fichier déposé à la banque par l'utilisateur, les règlements
passent par le service d'écriture de la Comptabilité, jamais en double.
*Aucun envoi à la banque* : ni EBICS, ni API bancaire.

Décisions (`D-SEPA-*`) et amendements proposés : link:DECISIONS.adoc[].
Référence du contrat : link:doc/api/sepa.adoc[].

== Fonctions

[cols="1,3",options="header"]
|===
|Fonction |Dans SEPA

|Virements fournisseurs
|`pain.001.001.09` (guides client-banque de l'EPC, version 2019 des
messages) : lots tirés des factures fournisseurs non lettrées, montant
ouvert exact, date d'exécution, référence de bout en bout, communication
libre, RF ou structurée belge, adresse hybride.

|Prélèvements SDD Core
|`pain.008.001.08` : mandats (RUM, date de signature, récurrent ou
ponctuel, révocation, expiration à 36 mois), séquences FRST, RCUR, OOFF,
identifiant créancier SEPA (ICS), amendement de l'IBAN.

|Contrôles
|IBAN (clé modulo 97, longueur du pays), BIC, ICS, jeu de caractères SEPA
et translittération des accents, jours ouvrés TARGET, écritures toujours
ouvertes. Fichier relu par un contrôle structurel, et validé contre le XSD
officiel quand l'exploitant le dépose (`PARTIDUO_SEPA_XSD_DIR`).

|Validation
|Préparer (le lot est soumis au service d'approbation du cœur), puis
approuver dans l'écran commun « Approbations », après une
authentification forte récente ; validation à une ou deux personnes selon
le réglage de la société (`approval_mode`). Un lot modifié après sa
soumission n'est pas exécuté (empreinte).

|Fichier et émission
|Fichier conservé en pièce jointe, téléchargeable ; émission confirmée par
l'utilisateur (date de dépôt) ; lot rouvert tant qu'il n'est pas émis.

|Règlements
|Une écriture par paiement par `Partiduo::Api::Accounting.post_financial`,
lettrée avec la facture, passée à l'émission ou proposée ; facture réglée
ailleurs jamais réglée deux fois ; règlement extourné de nouveau à passer
(`entry.cancelled`).
|===

Correspondance avec l'application d'origine : l'état « nouveau » devient un
lot en préparation, « déposé » un lot émis ; le compte bancaire est celui de
la fiche Banque du journal financier ; le `pain.001.001.03` devient le
`pain.001.001.09` (D-SEPA-001, D-SEPA-014).

----

├── partiduo-sepa.cr             # point d'entrée du shard

    ├── app.cr, manifest.cr      # code SEPA, permissions, menus, abonnement
    ├── models/                  # tables sepa_*
    ├── migrations/              # 0001 : tables et contraintes
    ├── services/                # codes, jeu de caractères, calendrier, lots, mandats, règlements (interne)
    ├── xml/                     # production pain.001 / pain.008, contrôle structurel, XSD par libxml2
    ├── api/                     # contrat public Sepa::Api
    └── locales/                 # fr, en, nl
ui/
└── bulma/                       # interface pour partiduo-ui-bulma (application « sepa_ui »)

    ├── handlers/, templates/sepa/, assets/sepa/, locales/
spec/fixtures/xsd-minimal/       # schéma minimal des specs (pas le XSD officiel)
----

== Composer une distribution

[source,crystal]
----
require "partiduo-ui-bulma/partiduo_ui"
require "partiduo-sepa"
require "partiduo-sepa/ui/bulma"
# installed_apps += Sepa::INSTALLED_APPS + Sepa::Ui::INSTALLED_APPS
# ligne de commande : require "partiduo-sepa/cli"
----

L'extension exige la Comptabilité (`depends_on "ACCOUNTING"`) et un journal
financier adossé à une fiche Banque dotée de son IBAN (et de préférence de
son BIC) ; elle s'active par dossier (`Partiduo::Api::Modules.activate`,
écran « Modules »). Pour les prélèvements, renseigner l'identifiant
créancier SEPA (ICS) dans la configuration de la société (« Paramètres ›
Société ») ; la validation à deux personnes s'y règle aussi.

Depuis 0.1.3 (contrat du cœur 0.17.0), la migration `0002` reprend l'ICS
et la validation à deux des anciens réglages de l'extension dans la
société, et repasse en préparation les lots qui attendaient leur
approbation selon l'ancien mécanisme (D-SEPA-016, D-SEPA-017).

Validation XSD (facultative) : déposer les schémas officiels
`pain.001.001.09.xsd` et `pain.008.001.08.xsd` dans un dossier et le
désigner par `PARTIDUO_SEPA_XSD_DIR` ; ils ne sont pas fournis (licence,
D-SEPA-012).

== Développement local

`shard.yml` et `shard.lock` référencent les shards maison sur GitHub
(`aloli-crystal/*` et `aloli-partiduo/*`), suivis par branche. Le verrou
versionné ne contient aucune dépendance `path:` : les ports FreeBSD et la CI
l'exigent.

Pour travailler sur les copies de travail voisines (`../../prod-crystal/<nom>`
et `../partiduo-<dépôt>`), lancer :

[source,sh]
----
scripts/override-local.sh
----

Le script génère un `shard.override.yml` *local et non versionné* (ignoré par
git), installe les shards, puis remet `shard.lock` à son état versionné.
Une copie de travail absente reste prise sur GitHub.

Pour régénérer le verrou versionné, supprimer d'abord l'override local :

[source,sh]
----
rm -f shard.override.yml
SKIP_MARTEN_CLI_PRECOMPILATION=1 shards update
scripts/override-local.sh   # retour au mode local
----
